## Evidencia y alcance

El usuario acreditó 28/28 Node y 0/1 Electron. El runner se detuvo en «Destino válido no abre ventana», condición compuesta que no distinguía ausencia de ventana y detección de destino. No se atribuye la causa raíz al hit-test ni a Pointer Capture sin datos del incidente nativo.

Se ejecutó un caso aislado en Chromium 144 mediante CDP con los módulos de producción (sin Vue, BrowserWindow ni IPC real), tanto antes como después: en pestañas nuevas se detectó el grupo central, no se solicitó ventana y se liberó el puntero al soltar. La condición también ocurrió con el baseline, no equivale a una reproducción del fallo local de Electron. No se cambia el mecanismo de captura basándose en ella.

## Corrección acreditada y observabilidad

`formatWebGLFailure` perdía el mensaje original de error si `data` estaba presente. La prueba de ese caso falla con el formatter anterior y pasa con el nuevo. Se conservan ambos campos, sin modificar el criterio de aceptación.

El propietario `dock-gesture.js` ofrece una suscripción opcional `observeDockGesture` para registrar panel, documento/ventana de origen, identidad y captura efectiva, posiciones cliente/pantalla/editor, hit-test, motivo, destino, solicitudes de ventana, confirmación y cancelación. No hay emisión continua ni nueva autoridad de captura cuando no existe observador. La fixture suscribe el observador y mantiene buffers acotados a 24 registros; el runner conserva 20 entradas y 20 eventos de ventanas. El runner separa las dos aserciones originales y las registra ambas antes de interrumpirse, exigiendo explícitamente la zona central y ausencia de ventana registrada o BrowserWindow de panel. Registra estado inicial/final, layout, límites de contenido y zoom. No se cambia el modelo de distribución, el umbral, el orden del gesto, el cálculo de coordenadas, las ventanas, el runtime ni las protecciones de ratón. No hay nuevas dependencias.

## Continuación: transición de foco durante apertura nativa

Baseline de entrada: 4.425 archivos; CRC correcto. El último log local acredita once checks de Electron hasta la creación de BrowserWindow y la identidad flotante. Se registra `native-request` al alcanzar 24 px sin destino, seguido de `cancel` con `native: true`, `actualCapture: false`, `focused: false`, `reason: blur`. El siguiente movimiento y liberación llegan al Editor, pero el gesto ya fue retirado. QA manual del usuario: la ventana independiente no vuelve a acoplar al arrastrarla. No se acredita que ambos fallos tengan idéntica causa.

`dock-gesture.js` marca la solicitud nativa antes de publicar el cambio de layout. La transición de foco puede comenzar solo durante la apertura propia (ventana temporal de 1.200 ms); el documento iniciador conserva la autoridad, no se recaptura Pointer Lock ni se transfiere implícitamente Pointer Capture. Las entradas posteriores deben pertenecer al gesto original y existir foco en el Editor o en el documento registrado para ese panel. Sin captura efectiva se conserva una espera acotada de 1.200 ms desde la última entrada válida. Pérdida ordinaria de foco, cancelación real, botón liberado sin pointerup, nuevo clic, Escape, foco ajeno, pagehide o timeout limpian la transición. Escape se escucha también en la ventana relacionada. No se garantiza continuidad si el compositor deja de entregar entradas al documento original. El umbral, hit-test y modelo de layout no se modifican.

Los encabezados de `AppWindow.vue` y `FloatingEditorWindow.vue` excluyen del arrastre del SO toda la franja de herramientas acoplables, no solo el texto de la pestaña. Delegan al mismo `startDockGesture` y excluyen botones, enlaces y campos. Se conserva el arrastre del sistema para ventanas no acoplables. Es una mejora del área de entrada, no una prueba de la causa raíz del fallo manual.

La documentación oficial de Electron (https://www.electronjs.org/docs/latest/api/browser-window) indica que `showInactive()` y `setPosition()` no están soportados bajo Wayland nativo, y que `getPosition()` devuelve [0,0] en ese backend. El log local tiene sesión Wayland, pero ello no acredita por sí mismo el backend Ozone efectivo. El runner permite `LF_QA_DOCK_BACKEND=x11` o `wayland` explícitos; en X11 solicitado y DISPLAY disponible selecciona XTEST salvo override. Registra el backend solicitado y geometría de contenido y zoom para contrastar coordenadas; el valor solicitado no certifica el backend efectivo. El arranque productivo predeterminado no cambia; ninguna dependencia npm nueva. Para evaluación manual XWayland, compilar antes y lanzar `./node_modules/.bin/electron --ozone-platform=x11 .`. No se añade ese flag al arranque normal. Cambiar el default requiere evidencia y Amendment.
